# 归档中断后的人工核对与恢复

本指南对应当前 `state_schema.py`、`sessions.py` 和 `panel.py`，不是自动恢复工具。存档库及其 `.trash` 共用库级排他锁，受保护操作再获取状态锁；`load_state`、`save_state`、`transact_state` 和面板的相关读取、队列操作会检查 `<state>.archive-pending` 与库级 `.ww-session-transaction-pending`，发现任一标记即拒绝继续，不解析、验证或修复记录。列表可能显示 `pending_review`。不要反复重试写入，也不要仅为解除阻塞而删除 pending。

存档移入回收站或还原时，主存档与识别到的备份、世代日志、快照、行动队列和趋势侧写及快照的关联侧写一起迁移；迁移前写入库级及各路径 pending，目标已存在时拒绝覆盖。异常或崩溃可能留下部分迁移，必须核对源、目标及全部标记，不能假定已完成或已回滚。

## 1. 停写并保全

1. 停止所有可能操作该存档的 MCP、CLI、脚本和其他进程，包括不遵守 `state_lock` 的写入者；确认没有仍在执行的操作。锁文件本身不是进程停止的证据，不要通过删除锁文件解除锁。
2. 在停写后，将库级 `.ww-session-transaction-pending`、源和目标目录中的状态文件、所有相关 `<state>.archive-pending`、`<state>.bak`、所有世代的 `<state>.log.jsonl` 和 `<state>.log.<generation>.jsonl`、相关快照及其他侧写文件一并完整复制到受保护的位置。保留目录结构、文件原始字节及存在/缺失情况，并核对副本；保留同目录可能残留的 `.ww_state_*.tmp`、`.ww_pending_*.tmp` 和 `.ww_backup_*.tmp`，不要假设它们一定属于本次事务。记录程序版本、错误和文件元数据。备份可能包含敏感游戏数据，应限制访问。
3. 保留不可改动的原始证据，在独立副本上做只读检查和试验；不要让应用或其他进程写入证据。`.bak` 是尽力创建的旧状态备份，普通 I/O 错误可使备份失败而状态替换仍继续，因此不能假定其存在、新鲜或与归档一致。

## 2. 理解记录与检查字节

`_save_state_unlocked` 在有归档条目时先写并同步临时状态，再发布 pending，追加并同步归档，尽力备份旧状态，最后以 `os.replace` 替换状态并尝试清理 pending。清理失败可留下 pending，即使操作已提交。保存失败时恢复调用方内存对象，不保证磁盘归档已回滚。

当前 pending 是 JSON 对象，包含以下字段；它不是经过认证的事务日志：

| 字段 | 当前实现含义 |
|---|---|
| `generation` | 目标状态的 `archive_generation`，缺省或假值按 0 处理；0 对应 `<state>.log.jsonl`，其他值对应 `<state>.log.<generation>.jsonl`。 |
| `existed` | 追加前目标归档是否存在；不是当前存在性的保证。 |
| `offset` | 追加前归档文件的字节大小；不存在时为 0。 |
| `length` | 本次准备追加的 UTF-8 字节长度，包含平台换行。 |
| `sha256` | 准备追加字节的 SHA-256 十六进制摘要，不是整个归档的摘要。 |
| `state_before` | 替换前状态文件原始字节的 SHA-256；当时不存在则为 `null`。 |
| `state_after` | 临时新状态文件原始字节的 SHA-256。 |

只在副本上核对 pending 是否完整且字段类型、范围合理；损坏、旧格式或无法解释的记录都视为未知，不作推断。对照状态原始文件字节的 SHA-256 与 `state_before`、`state_after`，也检查状态 JSON 中的 `archive_generation`、`archived_events`、`event_log` 和业务内容，与快照及操作记录交叉核实。`archived_events` 是状态中的计数，不是可用于截断的字节偏移或完整历史证明。对照记录中的 `generation` 找到目标归档，同时保留并检查所有其他世代；快照回退后不同世代可能包含仍须保留的历史。

在目标归档副本上按**字节**检查大小、`offset`、`length` 和区间 `[offset, offset + length)` 的 SHA-256；不要按字符数或行数替代字节数，也不要重新序列化 JSON 后比较摘要。文件缺失、长度不足、区间不匹配、额外尾部、状态或世代不一致时保留全部数据并继续调查。`existed: false` 或 `offset: 0` 本身不能证明现有文件可删除；区间之后的未知尾部必须原样保留。

SHA-256 这里只能辅助比较字节是否一致：记录和数据均可能被修改、伪造或来自未知事务，摘要不提供来源认证、防篡改证明或事务归属证明。即使摘要一致，也不能单凭它认定某段数据可安全删除或重做。

## 3. 人工判断与处置边界

- 状态字节匹配 `state_after` 且结合可信的独立证据确认该操作已提交时，不要重做该操作或再次追加条目；先核对归档和业务结果。状态匹配本身不是认证证明。
- 状态匹配 `state_before` 或原状态缺失，不能单凭此认定追加未发生或允许重试；归档可能已经部分或全部写入。状态同时匹配两个摘要时也不能据此判断提交顺序。
- 如果不能证明记录来源、提交状态、归档段的归属与完整边界，或发现未知尾部、竞争写入、损坏、缺失及其他冲突，保持停写并保留全部证据；不可自动截断、删除归档或清除 pending。必要时由熟悉该存档的人员依据独立可信证据进行个案处置。
- 只有在独立证据充分、已保存完整备份、确认处理方案不会丢失或重复已提交历史后，才由人工在工作副本上验证处置结果；确认状态、所有归档和业务结果一致后，再以可回滚的方式恢复现场并解除 pending 阻塞。记录具体决策与操作。没有足够证据时不恢复写入。

## 4. 版本回退和故障范围

不要用旧版程序绕过 pending 阻塞或直接打开原始证据：旧版可能忽略记录，或采用不同的归档/截断语义，导致历史丢失、重复或状态与归档分叉。必须保留完整备份，在隔离副本上核实旧版的实际行为和兼容性；不能证明安全时继续停写。

当前子进程中断回归覆盖部分进程崩溃窗口；文件 `fsync` 和原子替换的使用不等于对断电、存储设备缓存或目录持久性的保证。断电后尤其不能把缺失或匹配的文件当作提交状态的唯一证据。
